RAG分词实战随记

2026年8月21日 · 1 分钟 · 184 字 · beyond

RAG 分词（Chunking）是 RAG 系统中最容易被忽视、但对效果影响最大的环节。行业共识是：分块质量决定了 RAG 系统成败的 70%。

以下是经过实战验证的比较好的实践。

核心原则：能不切就不切#

切分不是越细越好。每多切一次，就是对语义完整性的一次破坏。最佳策略是**“粗中有细”**——既尊重文档的自然结构，又控制块大小在合理范围内。

关键参数设置#

Chunk Size（块大小）#

没有万能值，但有黄金区间和决策框架：

文档类型推荐 Chunk Size说明
技术文档/代码100~300 tokens保持函数、类完整
FAQ/短问答100~300 tokens一问一答天然成块
通用文本250~512 tokens业界常用起点
论文/法律文本500~1000 tokens保留上下文连贯性
文档总结类800~1500 tokens需要更多上下文

硬上限：绝不能超过 Embedding 模型的最大上下文长度（如 BERT 类通常 512 tokens，text-embedding-3-small 支持 8192 tokens）。

Overlap（重叠长度）#

  • 通用比例：Chunk Size 的 10%~20%（如 chunk_size=500，overlap=50~100）
  • 关键信息密集场景（法律条款、医疗术语）：可提升至 25%~30%
  • 语义密度低的段落：可降低至 5%~10%

Overlap 的核心目的是防止句子或关键信息被"腰斩"，保证上下文连贯。

切分策略选型（从低到高）#

策略一：递归字符分块（推荐作为默认方案）#

LangChain 等框架的默认推荐方法。按分隔符优先级递归切分：["\n\n", "\n", "。", " ", ""]，优先按段落切，段落太大再按句子切，以此类推。

  • 优点：保留段落/句子完整性，实现简单
  • 缺点：对表格、代码等复杂结构效果一般
  • 适用：快速原型、通用文档

策略二：基于文档结构分块#

利用 Markdown 标题、HTML 标签、章节等原生结构切分。

  • 优点：逻辑清晰，检索精准
  • 缺点：依赖文档格式标准化
  • 适用：技术手册、API 文档、产品说明书

策略三：语义分块（Semantic Chunking）#

计算相邻句子的 Embedding 相似度，在语义发生显著变化时切分。

  • 优点：块边界天然语义完整，检索精度最高
  • 缺点：计算成本较高
  • 适用：法律合同、医疗报告、学术论文

策略四：父子索引（Parent-Child Indexing）#

被称为"RAG 大杀器"。检索用小块（Child，200400 tokens），生成用大块（Parent，10002000 tokens）。

  • 优点：兼顾检索精度和上下文完整性
  • 缺点：实现复杂度较高
  • 适用：对回答质量要求高的生产环境

策略对比一览#

策略检索精度上下文完整性计算成本适用场景
递归分块中中低快速原型、通用文档
结构分块中高高低结构化文档
语义分块高高中高法律、医疗、学术
父子索引高最高中高生产级高质量 RAG

五个实战技巧#

元信息增强（几乎零成本，回报巨大）#

在每个 Chunk 开头附加来源信息（章节标题、层级路径等），给 LLM 一个"定位锚点"。例如 Markdown 文档切分后，在每块前面加上它所属的标题层级。

表格处理：表头复制到每个子块#

表格切分后，每个子块必须带上完整表头。实测表格类问题正确率可从 43% 提升到 78%。

列表前导句强制保留#

识别列表的前导句（如"以下情况不在赔付范围内："），复制到每个列表子项 Chunk 的开头。否定性查询召回率可从 0.58 提升到 0.83。

低质量过滤#

切分后过滤掉少于 50 字的无意义片段、重复内容及无关信息。

Lazy Chunking（惰性切分）#

在满足最大长度限制前，尽量把内容塞进同一个 Chunk。现代大模型"不怕信息噪音但怕信息碎片"，给模型多一点上下文，让它自己甄别有用信息。

调优流程（数据驱动）#

不要凭感觉设参数，按以下流程实验：

  1. 构建评估集：准备 20~50 条代表性 Query + 人工标注的标准答案
  2. 设定 Baseline：递归分块 + 512 tokens + 20% overlap
  3. 逐一对比：切换语义分块、父子索引等策略
  4. 量化评估：用 RAGAS、TruLens 等工具计算 Context Precision、Recall、Faithfulness 等指标
  5. 持续迭代：生产环境监控实际 Query，定期 Re-evaluate

总结#

先用递归分块跑通 MVP，再用父子索引或语义分块提升质量，用元信息增强和表格/列表特殊处理做精调，最后用评估数据驱动参数优化。切分策略选对了，胜过盲目堆模型参数。
