如何搭建RAG评测体系

2026年9月21日 · 1 分钟 · 188 字 · beyond

没有评测的优化，本质上是瞎调。很多人做 RAG 只会埋头调参数——换 embedding、改切片、加重排序，却说不清"这次改动到底让效果变好了还是变差了"。原因很简单：缺一套能量化、可复现的评测体系。

这篇文章就把"如何从零搭建一套 RAG 评测体系"讲透，核心是四步：建评测集 → 定指标 → 跑评测 → 上线监控闭环。

一、为什么必须先有评测体系#

RAG 系统由"检索 + 生成"两段组成，任何一段的改动都可能牵一发而动全身。凭感觉判断效果有三个致命问题：

  • 不可复现：换个时间、换批问题，结论就变了。
  • 无法归因：效果下降了，不知道是检索没召回，还是模型编造了内容。
  • 盲目优化：调了一堆参数，其实是负优化都不知道。

评测体系的价值，就是把"我觉得变好了"变成"召回率从 0.72 提升到 0.85，幻觉率从 8% 降到 3%"。

二、第一步：建评测集（所有评测的根基）#

评测集质量决定了评测结论的可信度。一份合格的评测集必须满足三个条件。

1. 来源要真实#

大部分问题应来自真实用户（线上日志、客服工单、社区提问），而不是自己拍脑袋造。自己造的问题往往过于"标准"，覆盖不到真实场景里的口语化表达、错别字、模糊指代。

2. 覆盖要全面#

按约 7:2:1 的比例组织三类问题：

类型占比说明示例
常见问题70%高频、主流场景“怎么申请退款？”
边缘问题20%长尾、跨文档、多跳推理“A 套餐和 B 套餐哪个更适合企业用户？”
诱导性问题10%故意挖坑，考验幻觉抵抗“你们产品能治疗癌症吧？"（实际没有此功能）

诱导性问题尤其关键——它专门用来检测模型会不会"顺着用户的话编造不存在的信息”。

3. 标注要规范#

每条评测数据至少包含四要素：

  • 问题（Query）
  • 标准答案（Ground Truth）
  • 对应的参考文档/切片（Reference Context）：用于判断检索是否召回正确
  • 评分规则：明确定义"完全正确 / 部分正确 / 答非所问 / 幻觉"的判定标准

建议：评测集规模起步 50~100 条，随业务迭代持续扩充。标注最好由两人独立打分再交叉校准，减少主观偏差。

三、第二步：定指标（不同阶段看不同指标）#

RAG 要分段评测，不能把检索和生成混为一谈。

检索阶段指标#

指标含义为什么重要
召回率 Recall@KTop-K 结果里是否包含正确答案对应的文档最大瓶颈：召回不上来，生成再强也没用
精确率 Precision@KTop-K 里有多少是相关的噪音文档过多会干扰生成
MRR / Hit Rate正确文档排在第几位排序越靠前，生成越容易抓到重点

生成阶段指标#

指标含义
准确率（Answer Correctness）答案是否与标准答案一致
忠实度（Faithfulness）答案是否只基于检索到的上下文，有没有编造
幻觉率（Hallucination Rate）生成了文档中不存在信息的比例
答案相关性（Answer Relevancy）答案是否切题、答非所问

端到端指标#

  • 用户满意度：点赞/点踩、追问率、转人工率。
  • 人工抽检校准：自动指标再准，也要定期用人工抽检来校准，防止"指标好看但体验差"。

优先级提醒：先解决检索召回率。大多数 RAG 系统的问题根源都在检索段，而不是生成段。

四、第三步：跑评测（工具与流程）#

常用评测工具#

  • RAGAS：开源，提供 Faithfulness、Answer Relevancy、Context Precision/Recall 等一整套指标，支持"用 LLM 当裁判"（LLM-as-a-Judge）。
  • TruLens：可视化追踪 + 评测，适合调试和归因。
  • 自建脚本：对检索段指标（Recall@K、MRR）用代码直接算，最可靠。

评测流程（数据驱动）#

  1. 设定 Baseline：记录当前版本的各项指标作为基准。
  2. 单一变量对比：一次只改一个因素（如只调 chunk size），跑评测对比。
  3. 自动 + 人工双轨：自动指标批量跑，人工抽检校准裁判模型是否可信。
  4. 回归测试：每次改动都要跑全量评测集，防止"修好一个坑，踩出三个新坑"。
  5. 版本留档：把每次评测结果与代码/参数版本绑定存档，便于回溯。

LLM-as-a-Judge 有偏差（如偏爱长答案、偏爱自己的输出）。要用人工标注结果定期校验裁判模型的一致性。

五、第四步：线上监控闭环#

线下评测再好，上线后效果仍可能下降——因为你永远不知道用户下一步会问什么。线上监控要搭三层：

层级监控内容
底层：基础性能接口延迟、报错率、token 成本
中层：效果指标回答准确率、幻觉率、相关度；定期抽样跑离线评测
上层：用户反馈闭环点踩、转人工的问题自动收集为 bad case，归因后回流评测集

反馈闭环是精髓：线上暴露的 bad case → 归因分析 → 补进评测集 → 驱动下一轮优化。这样评测集会随真实场景不断进化，越来越贴近用户。

效果下降怎么排查？#

按固定顺序逐层定位根因：

  1. 检索召回率有没有下降？（最常见）
  2. 模型版本有没有更新？（供应商静默升级常导致效果漂移）
  3. 知识库有没有变化？（文档增删改导致切片/索引失配）

总结#

搭建 RAG 评测体系，就是打通一条 “建评测集 → 定分段指标 → 跑数据驱动评测 → 线上监控闭环” 的链路。评测集要真实、全面、标注规范；指标要分检索段（召回率是最大瓶颈）和生成段（准确率、幻觉率）分别量化；线上用三层监控 + bad case 回流，让评测集持续进化。记住：证明系统准确靠的是评测体系，而不是优化手段本身。先有评测，再谈优化。
