什么是skill

2026年8月19日 · 3 分钟 · 568 字 · beyond

Skills 是什么？#

Skills 本质上就是把某类事情"应该怎么做"封装成一个可复用、可自动触发的能力模块。

它和 AGENTS.md 的区别：

概念类比作用
AGENTS.md岗位说明书告诉 AI “你是后端工程师”
Skills岗位培训手册告诉 AI “写 Go 代码时按这套流程来”
Prompt口头交代每次临时说一遍，说完就忘

一句话：AGENTS.md 定义身份，Skills 封装经验，Prompt 处理临时需求。

Skills 的核心结构#

一个 Skill 就是一个文件夹，核心只有一个文件 SKILL.md：

my-skill/
├── SKILL.md          ← 唯一必需，包含元数据 + 执行指令
├── scripts/          ← 可选，可执行脚本
├── references/       ← 可选，参考文档
└── assets/           ← 可选，模板资源

SKILL.md 的基本语法：

---
name: skill-name
description: 说明该 Skill 的功能以及适用场景
---

## 使用场景
当需要 xxx 时使用本 Skill

## 执行步骤
1. 第一步做什么
2. 第二步做什么
3. 第三步做什么

## 输出规范
- 输出格式要求
- 代码风格要求

其中 name 和 description 是必填项，description 尤其重要——AI 靠它判断"什么时候该调用这个 Skill"。

针对 Go 后端的 Skill 定义示例#

示例一：Go 代码审查 Skill#

目录结构：

skills/
└── go-review/
    └── SKILL.md

SKILL.md 内容：

---
name: go-review
description: |
  对 Go 代码进行专业级审查，检查代码规范、错误处理、并发安全、性能问题。

  Use when:
  - 用户要求审查 Go 代码
  - 提交前代码检查
  - 检测 goroutine 泄漏、竞态条件

  Don't use when:
  - 非 Go 语言的代码审查
  - 纯前端代码检查
---

## 审查清单

### 1. 代码规范
- 包名小写单字，不使用下划线
- 变量命名简短有意义，遵循 Go 命名惯例
- 导入包按标准库 / 第三方 / 本项目分组排序
- 公共 API 必须有 godoc 注释

### 2. 错误处理
- 所有错误必须显式检查，禁止忽略 if err != nil
- 使用 %w 包装错误，保留错误链
- 禁止使用 panic（除 main/init 外）
- 错误信息要有上下文，便于排查

### 3. 并发安全
- goroutine 必须有退出机制（context 取消或 channel 信号）
- 检测共享内存访问是否有同步保护
- channel 使用后必须关闭或由发送方管理
- sync.WaitGroup 的 Add 必须在 goroutine 外部调用

### 4. 性能
- 切片和 map 尽量预分配容量
- 避免在循环中创建不必要的对象
- 高频分配对象考虑使用 sync.Pool
- 字符串拼接使用 strings.Builder

### 5. 测试
- 使用 table-driven tests
- 测试覆盖率不低于 80%
- 基准测试覆盖关键路径

## 输出格式
对每个问题输出：
- 文件和行号
- 问题描述
- 修改建议
- 对应的规范依据

示例二：Go 微服务骨架生成 Skill#

---
name: go-microservice
description: |
  生成生产级 Go 微服务骨架代码，包含 Gin 路由、zap 日志、pprof 监控、
  优雅关闭、配置加载等完整基础设施。

  Use when:
  - 用户要求创建新的 Go 微服务项目
  - 用户要求生成服务骨架或脚手架

  Don't use when:
  - 用户只是问 Go 语法问题
  - 非微服务场景（如 CLI 工具、脚本）
---

## 技术栈
- Web 框架：Gin
- 日志：uber/zap（JSON 格式 + level 控制）
- 配置：Viper（config.yaml）
- 监控：net/http/pprof（仅 debug 模式开启）
- 优雅关闭：监听 SIGINT/SIGTERM

## 项目结构
- cmd/server/main.go：入口，负责启动和优雅关闭
- internal/handler/：HTTP handler
- internal/service/：业务逻辑
- internal/repository/：数据访问
- internal/middleware/：中间件
- pkg/config/：配置结构体
- config/config.yaml：配置文件
- Makefile
- go.mod

## 生成步骤
1. 创建目录结构
2. 生成 main.go：初始化日志、加载配置、注册路由、启动 HTTP Server、监听信号优雅关闭
3. 生成 config.yaml：包含 server、log、database 三个配置段
4. 生成 Makefile：包含 build、run、test、lint 四个 target
5. 生成 go.mod：指定 Go 版本和依赖

## 输出规范
- 所有函数必须有错误返回
- 使用 context.Context 传递请求上下文
- 中间件链式注册：Recovery → Logger → CORS → Handler
- 代码风格遵循 Effective Go

示例三：Go 单元测试生成 Skill#

---
name: go-test-gen
description: |
  为 Go 函数自动生成 table-driven 单元测试，覆盖正常、异常、边界场景。

  Use when:
  - 用户要求为 Go 函数生成测试
  - 用户要求提升测试覆盖率

  Don't use when:
  - 非 Go 语言的测试生成
  - 用户要求写集成测试或 E2E 测试
---

## 测试规范
- 使用 table-driven tests 模式
- 测试文件命名：xxx_test.go
- 测试函数命名：TestXxx(t *testing.T)
- 每个测试用例使用 t.Run() 子测试
- 使用 t.Helper() 标记辅助函数

## 覆盖场景
- 正常路径（happy path）
- 空输入 / nil 输入
- 边界值
- 错误路径（mock 依赖返回错误）

## 输出格式
func TestXxx(t *testing.T) {
    tests := []struct {
        name    string
        input   InputType
        want    OutputType
        wantErr bool
    }{
        {
            name:    "正常场景",
            input:   ...,
            want:    ...,
            wantErr: false,
        },
        // 更多用例...
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Xxx(tt.input)
            if (err != nil) != tt.wantErr {
                t.Errorf("error = %v, wantErr %v", err, tt.wantErr)
            }
            if !reflect.DeepEqual(got, tt.want) {
                t.Errorf("got = %v, want %v", got, tt.want)
            }
        })
    }
}

Skill vs AGENTS.md vs Prompt 对比#

维度AGENTS.mdSkillsPrompt
定义什么身份与边界做事方法临时指令
生效方式始终加载按需触发一次性
复用性项目级跨项目复用不可复用
类比岗位说明书操作手册口头交代
文件AGENTS.mdskills/xxx/SKILL.md对话框输入

编写 Skill 的三个关键技巧#

技巧一：description 要写清楚"什么时候用、什么时候不用"

这是 AI 判断是否调用 Skill 的唯一依据。写得模糊就会导致该触发时不触发，不该触发时乱触发。

技巧二：步骤要编号、无歧义

用 1. 2. 3. 编号，每步一个动作，避免"然后适当地处理一下"这类模糊描述。

技巧三：提供输出示例

给 AI 一个你认可的输出样本，比写十条规则都管用。

总结#

AGENTS.md 告诉 AI “你是谁”，Skills 告诉 AI “怎么干活”，Prompt 处理 “临时需求”。三者配合，AI 才能从"能聊天的模型"变成"能干活的工程师"。
